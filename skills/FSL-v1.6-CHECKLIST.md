# FSL v1.6 — Four-square release check

- [ ] **SPEC:** binding promises, project identity and version are stable; evidence scope and any authorized exceptions are clear.
- [ ] **PRIMARY LANE:** the declared deliverable passes its acceptance gates; component results are not overstated as E2E.
- [ ] **SECOND LANE:** the project's chosen documentation, AI material or other deliverable is usable, checked and aligned with SPEC.
- [ ] **MEMORY:** decisions, glossary and evidence links are understandable and current; memory has not invented law.

One reviewed project version; four exact lane commits and their evidence. Check the actual snapshot, not a moving branch name or an earlier green result. A 1–3 page letterhead, separate template/project versions and the ownership footer should be confirmed with the rendered documents.

**One version, four squares, all green.** This is a condition to establish, not an automatically granted status. No per-iteration checklist or YAML tracker is required by FSL.

After release: freeze the released SPEC. Clarify with APPENDIX, correct without changing intent with ERRATA, and make normative post-release changes only through AMENDMENT. The next release SHOULD absorb adopted errata/amendments into a new clean baseline.
