# FSL v1.5 — Generation Skill

Name: Four-Square Letterhead. Version: 1.5.  
Purpose: create, update, validate and recall a compact 1–3 page project constitution and working letterhead.

## Start with the owning project

Read the supplied project SPEC and actual artifacts before drafting. Identify the project repository and version. Put consuming-project work inside that repository; FSL's repository is for the reusable framework, method and clearly labeled reference samples. Never infer the project repository from an unrelated branch name, root commit or current working directory.

## Preserve the model

SPEC and MEMORY are fixed. Choose two durable middle concerns and their exact lane tokens. BASE/AI, CODE/DOCS, TOOLS/SKILL and other combinations are project choices, not universal requirements. Keep names consistent across pages, branches, evidence and versions. Touchpoints describe a path through the system; they are not branches.

Show the project version in the header and **Four-Square Template v1.5** in the footer on every page. Add the exact one-line footer axiom: **FSL owns the method. The project owns the work.**

`main1` means the project's own first, immutable root commit. Initial lane versions start from it; subsequent versions continue their corresponding lane lineage. `main` is accepted integration. vN in a lane name is the project release view, not the FSL template number.

## Write only what is needed

Use the one-page template by default. Fill purpose and boundary, then write the project's actual observable promises with stable clause IDs and an evidence reference. Do not present FSL method examples as newly approved project requirements. Use MUST/MUST NOT only for binding intent, SHOULD/SHOULD NOT for guidance and MAY for permission; render normative keywords in capitals, bold and underline. Preserve published clause IDs; do not recycle retired IDs.

Keep the development section to the initial sequence:

> I-001: tiny [input] -> [required touchpoints] -> [observable output] -> prove -> grow.

Adapt it to the actual project. The initial path and its touchpoints should be understandable from that line. Do not generate every later iteration, an iteration ledger, a YAML schema or separate PATH/MODE/GROWTH fields. Later work may grow naturally, split at a named midpoint contract or run independent E2E paths in parallel.

A component or partial-path check is not integrated E2E proof. A stub or fixture cannot prove the real integration it replaces. A declared touchpoint must actually be exercised for the coverage claimed; that does not mean its implementation must change.

## Essential references

Use `ITEM | INTENT / USE | CANONICAL SOURCE`, or a short prose line. Keep only material technology, library and reference choices. State an adopted MUST/SHOULD/MAY where relevant; link a mandatory choice to a SPEC clause ID. REUSE is using a capability; INHERIT is explicitly adopting a contract into SPEC; REFERENCE is consulting it without adopting its law. Add a pin only when a version/date/commit changes meaning. Do not invent a required dependency or turn a source link into authority by implication.

## Depth without duplication

1P contains the complete identity and working approach. 2P adds only needed interface/reference detail. 3P adds only needed release/evidence detail. Delete unused sections and move long inventories, logs and moving implementation details to project-local supporting files. The letterhead never exceeds three pages; supporting artifacts are not extra letterhead pages.

## Four-square release check

SPEC is stable; the main deliverable passes its gates; the second lane is usable and aligned; MEMORY is understandable. Use the project's own second-lane criterion—AI instructions, documentation or another deliverable—as appropriate. At release, record the four reviewed commits and evidence together; a short Markdown table or release-note line is enough. Git remains authoritative.

Scope proof using CLAIM / SCOPE / ENVIRONMENT / EVIDENCE / RESULT. Keep unknown claims NOT YET PROVEN; use NON-CONFORMANT for known binding violations. An exception requires explicit authority and scope, not merely a note. MEMORY may remember law; MEMORY cannot make law. Surface ambiguous normative intent instead of silently strengthening, weakening or inventing it.

## Generation and validation

Read the owning project -> choose 1P/2P/3P -> fill its contract and initial path -> add essential sources -> render DOCX/PDF -> inspect every page -> check identities and links -> package with checksums.

Check the actual PDFs for page counts, clipping, readable type and the footer on every page. Verify keyword emphasis in DOCX. Keep the editable DOCX and its rendered PDF aligned. Never label unchecked project boxes green, invent a commit, or equate file generation with a repository release. `FSL-v1.5-CHECKLIST.md` is a release aid, not an iteration tracker.
