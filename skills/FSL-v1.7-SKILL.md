# FSL v1.7 - Generation and adoption skill

Purpose: create, adopt, validate, recall and release a compact 1-3 page project letterhead. This skill implements the FSL v1.7 Constitution; it does not independently make law.

## Read the project before writing its contract

Identify the owning repository, actual artifacts, project/contract version, adoption scope and responsible authority. Read existing SPEC and applicable adopted changes. Never infer a repository from an unqualified branch name. Keep consuming-project work in that project's repository; the FSL repository holds its own framework and clearly labeled reference samples.

Start with SPEC / SYSTEM / AI / MEMORY. Only SPEC and MEMORY are fixed; keep justified existing middle-lane specializations. Present the project's completed FSL letterhead first inside SPEC, followed by supporting details and optional appendix, errata and amendments. Do not create empty lifecycle documents.

Ownership follows purpose, not author: product source and product checks are SYSTEM; AI instructions/skills/prompts/evaluations are AI; adopted requirements are SPEC; rationale and handover are MEMORY. An inactive AI scope must be explicit, not padded with invented agents or tests. Shared artifacts have one authoritative owner; generated copies do not create a second authority.

## Choose the adoption path

For a new project, recommend `I-001: tiny R-01 -> verify -> grow`. Keep only the initial sequence; do not predict every later iteration.

For an existing project, study or reverse-engineer as needed, identify a reviewed current-state commit/artifact baseline, distinguish OBSERVED / AS-IS from ADOPTED / INTENDED behavior, then define the FSL and critical routes. Historical and future iteration plans are optional. Do not rewrite history, force cosmetic branch renames or rebuild existing capabilities merely for FSL adoption. Unknown intent must be surfaced; do not infer a new obligation from a bug or a remembered decision.

For new repositories, initial lanes start at the first-commit root main1. For existing repositories, new adoption lanes may start at the reviewed adoption commit; preserve justified lineage. Never move main1 or manufacture historical branches. Subsequent lane versions continue corresponding predecessors. Branch suffixes follow project releases, not template versions.

## Make E2E visible

Show a primary route: `R-01: input -> required touchpoints -> observable output`. Give the expected outcome and applicable SPEC/route baseline, linked to relevant clause IDs. Add only other critical routes when useful. R-01 is a route ID, not an iteration or run number.

Before every route run, show all declared touchpoints. Retain PASS, FAIL or NOT RUN for every point, including unreached points, plus outcome and evidence. Record the run identity, actual implementation revision, applicable SPEC/adopted changes, route reference and environment. Use a normal log or the short run-sheet example in FSL-v1.7-ROUTES.md; do not introduce a run database or required history ledger.

Require connected workflow evidence, not a collection of independent component passes. Every required touchpoint and the expected output must be verified before claiming the complete route. A skipped point remains unproven. An exception does not turn it into a PASS. Never prefill success or silently reuse an older run's success. Do not delete a touchpoint to fit a passing subset.

Unchanged touchpoints can be verified without edits. AI is a runtime touchpoint only when the claim depends on it. Disclose fixtures/stubs and safe test environments. E2M/M2E stay partial; a named midpoint contract and a combined check are needed for integrated proof. Parallel routes keep separate results and verify shared contracts/state where they interact. A negative route may PASS by observing its expected rejection.

## Keep the letterhead small

Use 1P by default; 2P adds route/adoption detail and a reusable run-sheet example; 3P adds exact release identity and lifecycle details. Adapt rather than blindly retain explanatory template prose. Move detailed cases, logs and inventories to supporting project files; the letterhead stays within three pages.

Show separate project/contract and FSL versions on every page. Footer: **Four-Square Template v1.7** and **FSL owns the method. The project owns the work.** Normative terms are uppercase, bold and underlined. Topic labels alone do not create force. Preserve clause identity with baseline context; do not recycle IDs for unrelated requirements.

Keep only essential references: `ITEM | INTENT / USE | CANONICAL SOURCE`. State adopted force and a SPEC clause ID for a mandatory dependency. REUSE uses a capability; INHERIT adopts an identified contract/scope; REFERENCE consults without adoption. Pin a source version only when material. A link alone is not law.

## Apply the lifecycle

Before first release, revise reviewed draft SPEC directly. Appendix may support study or development without adding obligations. After release, preserve the baseline: appendix explains; errata corrects without changing intent; amendment changes intent explicitly.

A proposal is not adopted by being committed. An adopted amendment needs the base version, affected clauses, exact delta, authorized decision, effective scope/date and immutable record reference. Identify the effective change set and resolve overlaps before conformance claims. Reassess affected implementation and routes; adopted intent is not execution evidence. The next release records incorporated changes and becomes a new baseline.

## Verify, then publish truthfully

Read -> fill contract and route -> generate DOCX -> render PDF -> inspect every page -> check content/identities -> package -> verify unpacked files -> commit/release -> read back actual publication state.

Scope claims using CLAIM / SCOPE / ENVIRONMENT / EVIDENCE / RESULT. Missing evidence is NOT YET PROVEN; a known binding violation is NON-CONFORMANT. Never invent law, commits, approval or execution. MEMORY may remember law; MEMORY cannot make law.

Four release checks: SPEC stable; main deliverable verified; second concern aligned/usable or explicitly inactive; MEMORY understandable. Verify their exact integrated combination against critical routes, not just unrelated branch badges. Record the four reviewed commits; unchanged lanes need review, not ceremonial edits. Distinguish a local package, public branch release and GitHub Releases-page publication.

The Django sample is an illustration with all runtime touchpoints NOT RUN. Its document checks do not certify Django, an upstream adoption or a production workflow.
